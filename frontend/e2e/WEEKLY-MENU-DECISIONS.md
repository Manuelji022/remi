# Decisions real-stack E2E: scenarios and failure modes (written before implementation)

Scope: `?mock=decision-ok` and `?mock=decision-invalid` (honored only when `AI_WEEKLY_MENU_MOCK=true` and `NODE_ENV !== 'production'`) run the real `prepareWeeklyMenuDecision` adapter, the installed AI SDK `experimental_decide` and the real Gateway HTTP transport code against an in-process fake `fetch`. No network I/O, no key. Mock transport only: no claim about model quality or live Gateway behavior.

Scenarios (real server function, guard, PostgreSQL, browser):

- **A** `decision-ok` initial generation renders a preview; the selected candidate is the LAST criteria key sent in the request (non-first); one guarded attempt, lease released, nothing saved.
- **B** Changing one home slot's recipe with the preview selector makes no further `generateNextWeeklyMenu` call and no new attempt row; covered (office) slots stay without recipes.
- **C** Accept saves exactly the visible edited menu; reload shows it; the shopping list contains the swapped recipe's ingredient and not the replaced recipe's.
- **D** With an edited, unsaved preview, "Generate another" with `decision-invalid` shows the loss-confirmation dialog; after confirming, the request fails recoverably and the edited preview returns with identical assignments; the attempt is counted and no lease remains.

Failure modes each scenario must catch:

1. The mock scenario is honored without the mock gate, or reaches the network (the runner's loopback-only and non-local-socket checks must still pass).
2. Selection is a fabricated menu, the first candidate by default, or something other than the choice in the response body.
3. The fake transport is bypassed (singleton shortcut) because the fixture has too few recipes; the artifact records the candidate count and it must be greater than one.
4. Decisions generation skips the guard: no attempt row, or a lease left behind.
5. A manual edit triggers regeneration or an extra attempt, or the save differs from what is visible, or covered slots acquire recipes.
6. An invalid choice becomes a preview, loses or alters the edited preview, or leaves the page without the existing error UI.
7. Reruns differ: fixed seed, fixed ids, deterministic fake transport, harness-owned artifacts regenerated byte-for-meaning.

# Decisions pilot: failures specified before implementation

1. Unknown engine values activate Decisions, or break generation; the default must remain `legacy` for missing, blank or unrecognized values.
2. Planning or database reads happen inside the lease. A singleton must still consume one guarded action without contacting Gateway.
3. A fabricated choice, refusal, malformed answer, HTTP error, missing credential or invalid model becomes a successful preview. Regeneration must always throw. Initial generation throws for `auth`/`model-not-found`; for timeout, refusal, invalid choice, rate limit and unknown it returns the first validated local candidate with `selectionSource: 'local'` (one transport call, attempt consumed once, log outcome `local-fallback`, no message/recipe leak). A fallback that repairs a candidate, appears on regeneration or hides a credentials error is a failure.
4. Retries or multiple questions cause multiple paid calls; the sole choice has a total 20-second deadline and zero retries.
5. Decisions invents or repairs assignments instead of resolving an existing, complete, validated candidate. Covered slots, unavailable types and recipe ownership must remain authoritative.
6. State leaks identities, credentials, unrelated catalog recipes or ingredient metadata; history is invented when absent, partial history is dropped, or current/prior history is conflated with the previous proposal.
7. Unbounded state exceeds the budget, or ingredient names are silently truncated. Reduce finalists down to two, then fail if the complete state cannot fit 64 KiB of UTF-8.
8. Recipe text becomes instructions; the rubric makes nutritional assertions or treats unknown composition as known. Prefer avoiding clearly heavy pairs, then variety and current-week avoidance (prior week weaker).
9. Errors skip guard release, stale checks, auth/date validation or persist a menu before acceptance. Keep the existing guard and browser recovery harnesses.

The new transport tests must call the installed SDK's `experimental_decide` through a fake Gateway `fetch`, selecting a non-first candidate from multiple finalists. They establish transport and domain guarantees, not culinary model quality. Server-boundary tests cover routing, quota, preconditions and stale checks; the existing real-stack and UI harnesses cover persistence and preview recovery.

A fully covered week is not representable in the existing `lunch|dinner|both` schedule contract: Office and Eat Out each retain at least one home-planned slot per day. That case is deferred; this slice adds no unreachable quota bypass or synthetic scope. Empty recipe pools report `unavailableSlots`, not an all-away schedule.

## VPS operation and rollback

Keep `AI_WEEKLY_MENU_ENGINE=legacy` until credentials and a live quality comparison are explicitly authorized. An opt-in pilot uses `decisions`, server-only `AI_GATEWAY_API_KEY`, and `AI_WEEKLY_MENU_DECISION_MODEL` (default proposed model: `openai/gpt-6-luna-decisions`). `AI_WEEKLY_MENU_ENGINE` is trimmed and case-insensitive; only `decisions` opts in. Missing, blank or unrecognized values fail safe to `legacy` (never throw), with a single server-side warning per process for non-empty unrecognized values that does not echo the value. A blank `AI_WEEKLY_MENU_DECISION_MODEL` uses the default; a non-empty malformed model ID, an absent/blank remote credential (trimmed before use) fail explicitly before the lease. With `AI_WEEKLY_MENU_MOCK=true` (non-production) the mock path always wins and Decisions never calls the Gateway. A singleton requires no remote credentials. Model availability and culinary quality remain unverified without a live call.

Inject the key through the existing VPS process/container secret mechanism, never a `VITE_` variable or a tracked file. Allow outbound HTTPS to `ai-gateway.vercel.sh:443` from Node/Nitro. Configure the reverse proxy read/upstream timeout above the 20-second remote budget plus local planning and database time (for example, 60 seconds); the 60-second generation lease covers only the bounded selection. This PR performs no deployment or environment activation. Roll back by setting the engine to `legacy` and restarting the existing process/container; no migration is needed.

The adapter returns the existing `AiMenuResult` (`menu`, `recipeNames`, `unavailableSlots`) plus optional `selectionSource: 'local'` only on the initial-generation local fallback (never persisted). Remote errors on regeneration, and `auth`/`model-not-found` on any call, throw the existing recoverable generation error. With `decision-invalid`, initial generation therefore yields a local fallback and regeneration an error (scenario D unchanged). Diagnostics contain only rubric version, model ID, finalist count, UTF-8 state size, elapsed milliseconds, technical outcome and, on failure, a coarse category from an allowlist of error names (`timeout` including Gateway-wrapped aborts, `auth`, `model-not-found`, `rate-limit`, `refusal`, `invalid-choice`, `unknown`); no credentials, recipe text, raw provider error or invented token/cost values. State is minified, bounded to 64 KiB, and retains whole ingredient names while reducing finalists to at least two. History recipe IDs absent from the user's catalog (including client-supplied `previousProposal`) are sent as null. Local planning and all context reads precede lease acquisition; a valid singleton still uses it once.

## Real-stack Decisions run (mock transport, added with this E2E)

`decision-ok` and `decision-invalid` run in `generateNextWeeklyMenu` only when `AI_WEEKLY_MENU_MOCK=true` and `NODE_ENV !== 'production'`. They call the real `prepareWeeklyMenuDecision` with key `mock-not-a-key`, seed 17 and the in-process fake `fetch` in `src/features/weekly-menu/ai-mock-decision.ts` (a separate server-only module, because `ai-mock.ts` is also bundled for the browser). The fake answers the Gateway decision endpoint with the LAST criteria key (`decision-ok`) or `menu-unknown` (`decision-invalid`), and logs one `DECISION_MOCK_TRANSPORT` line (candidate count, choice, the candidate's assignments) that the harness reads from the dev-server log. The generation runs inside the existing `runAiGenerationWithGuard`. Engine selection for non-mock requests is unchanged; legacy remains the default.

The scenario runs after the 18 legacy results, clears the disposable database's request rows and saved week (the legacy flow spends the whole hourly quota), seeds 9 lunch + 9 dinner recipes with one ingredient each, sets Monday to Office (lunch covered), and then runs scenarios A–D (D before C, so the failed regeneration happens on an edited, unsaved preview).

```bash
cd frontend
REAL_STACK_BROWSER_BIN="$(realpath "$(agent-browser skills path core)/../../bin/agent-browser-linux-x64")" \
  pnpm e2e:real-stack e2e/real-stack/ai-weekly-menu.scenario.js
```

Expected: exit 0; the existing 18 `PASS` lines, then `PASS decision-ok…`, `PASS manual selector change…`, `PASS decision-invalid…`, `PASS accept persists the edited menu…`, the loopback check and the cleanup line. Harness-owned artifacts: `e2e/artifacts/weekly-menu-decisions-results.json` (scenario, input summary, seed 17, `weekly-menu-choice-v1`, candidate count 8, selected `menu-7`, selection source `decision (mock transport)`, per-assertion PASS/FAIL) and the screenshots `weekly-menu-decisions-results-{preview,manual,failure-recovery,accepted}.png`. Reruns produce a byte-identical JSON. This proves transport and flow wiring only: no live Gateway call, no model-quality claim.
